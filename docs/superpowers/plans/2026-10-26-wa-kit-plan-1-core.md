# wa-kit — Plan 1: rdzeń aplikacji referencyjnej i szwy — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Działająca aplikacja referencyjna (katalog główny repo) z rdzeniem (auth, organizacje, users, account, i18n, maile, env, logi, healthcheck) oraz biblioteka `wa generate`, która składa szwy (rejestr modułów, regiony markerów) z manifestów.

**Architecture:** Katalog główny repo **jest** aplikacją referencyjną (Next 16, kod z justnails-app i company-dashboard-app) — ma dokładnie układ wygenerowanego projektu. Obok leżą pliki tylko dla kitu: `packages/cli/` (`@wa-kit/cli`), `kit/`, `docs/`; CLI (Plan 2) ich nie kopiuje. npm workspaces `["packages/*", "apps/*"]` (statycznie, jak company-dashboard-app; moduł `worker` doda `apps/worker` i `packages/queue`). Odstępstwo od spec §6 (`app/`): zagnieżdżone workspaces npm nie działają, a identyczny układ upraszcza kopiowanie i `update`. Każdy obszar rdzenia to katalog `src/features/<x>/` z `module.ts`; rdzeń „widzi” moduły wyłącznie przez `src/modules.generated.ts` i regiony `wa:*:start/end`. Organizacje są w rdzeniu, `MULTI_ORG` przełącza tylko UI/przepływy.

**Tech Stack:** Node 22, npm workspaces, turbo, Next.js 16.3.x, React 19.2, TypeScript 5, Tailwind 4 + shadcn, Prisma 7 (`@prisma/adapter-pg`, multi-file schema), better-auth 1.6+ (pluginy `admin`, `organization`), next-intl 4, Resend + react-email, pino/otel jak w źródłach, zod 4, vitest 4, Playwright.

**Spec:** `docs/superpowers/specs/2026-10-26-wa-kit-design.md`

**Ten plan to 1 z 4.** Kolejne (pisane po zakończeniu poprzedniego):
- Plan 2 — CLI: `create-wa-app`, `wa add/remove/list`, manifesty `kit/modules/*.json`, test „każdy plik ma właściciela”, macierz składania w CI (na razie `core`).
- Plan 3 — moduły v1: `api-keys`, `audit-logs`, `uploads`, `worker`, `legal` (każdy jako zadanie), rozszerzenie macierzy CI.
- Plan 4 — `wa update` / `wa diff` (3-way merge), testy merge, dokumentacja procesu.

## Global Constraints

- Node 22 (`.nvmrc`: `22`), npm + `package-lock.json`. Bez yarn/pnpm, bez Nx.
- Wersje zależności jak w `justnails-app/package.json` (np. `next` `16.3.8`, `react` `19.2.3`, `better-auth` `^1.6.26`, `prisma`/`@prisma/client`/`@prisma/adapter-pg` `^7.4.2`, `next-intl` `^4.9.0`, `zod` `^4.3.6`, `vitest` `^4.1.2`). Nie dodawać zależności, których źródła nie używają, poza wymienionymi w zadaniach.
- Kod przenosimy ze źródeł, nie piszemy od zera. Źródła: `$WA_SOURCES/justnails-app` i `$WA_SOURCES/company-dashboard-app`, gdzie `WA_SOURCES=~/Documents/WebAmigos/_sources` (sklonować: `git clone --depth 1 https://github.com/webamigos/<repo> $WA_SOURCES/<repo>`). Usunąć logikę domenową i nazwy klientów (`JustNails`, `cba_live_`, Odoo, Monday itd.). Zamiast nazwy projektu placeholder `{{projectName}}` / `{{projectSlug}}` — w aplikacji referencyjnej wartości `WA App` / `wa-app` zdefiniowane w jednym miejscu: `src/shared/config/project.ts`.
- Struktura źródeł: `src/features/<x>/{contracts,components,services/{queries,commands}}`, `src/shared/{lib,components,utils,types,config}`, `src/components/ui` (shadcn), `src/app/[locale]/(auth|app)`, `src/proxy.ts`.
- Moduł nie edytuje plików rdzenia. Jedyne miejsca łączenia: `src/modules.generated.ts` i regiony markerów (lista w Task 3).
- Pliki generowane zaczynają się od linii: `// generated by wa — nie edytuj. Uruchom: npx wa generate` (w `.prisma`, `.ts`); w YAML i `.env.example`: `# generated by wa — nie edytuj …` dotyczy tylko regionu.
- Zmienne env rdzenia (dokładne nazwy): `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `RESEND_API_KEY`, `EMAIL_FROM`, `AUTH_PUBLIC_SIGNUP` (domyślnie `false`), `MULTI_ORG` (domyślnie `false`), `ADMIN_EMAIL`, `ADMIN_PASSWORD` (opcjonalne, tylko dla `admin:create`), `LOG_LEVEL`, `OTEL_EXPORTER_OTLP_ENDPOINT` (opcjonalne).
- Język domyślny `pl`; `en` dostępny w routingu (`localePrefix: "as-needed"`).
- Commity: Conventional Commits; każdy kończy się linią `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

- Bezpośredni `POST /api/auth/sign-up/email` przy `AUTH_PUBLIC_SIGNUP=false` musi zostać odrzucony po stronie serwera (ukrycie strony nie wystarcza) → test w Task 8.
- Użytkownik bez żadnego członkostwa (usunięty z ostatniej organizacji) loguje się → widzi stronę „brak dostępu do organizacji”, nie błąd 500 → test w Task 9.
- `admin:create` uruchomione drugi raz z tym samym emailem → nie tworzy duplikatu ani drugiej organizacji; nadaje `admin` i kończy kodem 0 → test w Task 10.

- `wa generate` na pliku bez markerów albo z uszkodzonymi markerami (start bez end, podwójny start) → błąd z nazwą pliku i markera, plik nienaruszony; drugie uruchomienie bez zmian nie zmienia żadnego bajtu → testy w Task 3.

### Task 3: `wa generate` — regiony markerów i rejestr modułów

**Files:**
- Create: `packages/cli/src/generate/regions.ts`, `packages/cli/src/generate/registry.ts`, `packages/cli/src/generate/targets.ts`, `packages/cli/src/generate/index.ts`, `packages/cli/src/bin.ts`
- Test: `packages/cli/src/generate/__tests__/regions.test.ts`, `registry.test.ts`, `generate.test.ts`

**Interfaces:**
- Consumes: `readKitState`, `installedModules` (Task 2).
- Produces:
  - `replaceRegion(content: string, file: string, marker: string, body: string): string` — marker `X` oznacza linie zawierające `wa:X:start` i `wa:X:end` (dowolny prefiks komentarza). Zastępuje wszystko między nimi `body` (z końcowym `\n`). Błędy: brak startu/końca, podwójny start, koniec przed startem → `Error("<file>: uszkodzony region wa:<marker>")`.
  - `renderRegistry(modules: { name: string; hasModuleTs: boolean; hasEnv: boolean; hasAuth: boolean; hasAuthClient: boolean; locales: string[] }[]): { server: string; client: string }` — dwa pliki TS.
  - `generate(projectDir: string): Promise<{ changed: string[] }>` — idempotentne.
  - CLI: `wa generate` (bin) wypisuje zmienione pliki, kod 0.
- Cele generowania (dokładnie te, w tej kolejności):
  1. `src/modules.generated.ts` (serwer): `export const modules = [...]` (importy `@/features/<x>/module`), `export const moduleEnvSchemas = [...]` (`@/features/<x>/env` → `envSchema`), `export const authPlugins = [...]` (`@/features/<x>/auth` → `authPlugin`), `export const moduleMessages: Record<Locale, () => Promise<Record<string, unknown>>[]>` (dynamiczne importy `@/features/<x>/i18n/<locale>.json`, namespace = `key` modułu).
  2. `src/modules.client.generated.ts`: `export const authClientPlugins = [...]` (`@/features/<x>/auth-client` → `authClientPlugin`), `export const clientModules` (tylko `key`, `nav`, `routePrefixes`, `roles` — bez importów serwerowych).
  3. `prisma/schema/auth.prisma`, region `relations` wewnątrz `model User` — pola z `schemaRelations` gdzie `model === "User"`; analogicznie region `relations` w `model Organization` w `prisma/schema/organizations.prisma`.
  4. `.env.example`, region `modules` — `NAZWA=example` z `env` manifestów modułów innych niż `core`, z komentarzem `# <moduł>` nad każdą grupą.
  5. `docker-compose.yml`, region `services` — zawartość plików `compose` modułów (wcięcie 2 spacje pod `services:`).
  - Wszystkie ścieżki względem katalogu projektu (= katalog z `.wa/kit.json`; w kicie: root repo). Plik docelowy z celów 3–5, który nie istnieje → pomijany bez błędu; istnieje bez markera → błąd jak w `replaceRegion`. Pole `workspaces` manifestu jest informacyjne (globy w `package.json` są statyczne).
  - Wykrywanie `has*` i `locales`: po istnieniu plików `src/features/<x>/{module.ts,env.ts,auth.ts,auth-client.ts,i18n/<locale>.json}` dla katalogów `<x>` wymienionych w `files` manifestu (wzorzec `src/features/<x>/**`). Moduł może mieć kilka feature'ów (np. `core`: `auth`, `organizations`, `users`, `account`, `dashboard`).
